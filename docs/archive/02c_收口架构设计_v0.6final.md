## 1. 实现方案总览（Implementation Approach）

### 1.1 核心难点与选型

| 难点 | 现状（已核实） | 方案 |
|---|---|---|
| 缺口识别只认 `source` 单数，忽略 `sources_present` | `gap_finder.py:57` `{f.source for f in day_features}`；`DerivedFeature.sources_present`（models.py:241）与 `DerivedFeatureIn.sources_present`（schemas.py:173）已存在且 ingest 已落库 | 以 `sources_present` 并集为权威，空列表 fallback `source`；`mic_opt` 可选、`health` 不强制；gap_id 稳定幂等 |
| 沙箱工具模板含情绪推断 | `tool_forge.py:83-113` `mood_check` 模板（mood_score 0-100 / trend improving|stable|declining）；`skill_induct.py:37` `"mood_check": "reflection_prompt"` | 删除 `mood_check` 模板与映射，不新增任何情绪推断工具 |
| 趋势接口基于 Checkin 情绪维度 | `trends.py` 全量基于 Checkin(mood/stress/energy/sleep_recovery)；`routes.py:512` `GET /v1/trends/summary` 在线 | 全仓 grep 验证无 Android/console/scripts 调用 → 移除公开契约；`build_trend` 保留为 case-review 内部 data_quality 用 |
| Android 窗口存在「先清 buffer 后落库」静默丢失窗口 | `SensingWindowScheduler.flushWindow` 先 `hub.clearAll()`（含 mic `snapshotAndClear`）再 `onWindowReady` 持久化；`flushedWindowStarts.add` 在最前 | 重构成 snapshot→extract→transactional persist→成功才 clear consumed；`onWindowReady` 返回 Success/Failure；bounded retry；失败可观察 |
| Skill 执行会话仅内存、暂停计时错误、process death 丢失 | `SkillCardHost.SkillRunSession` 纯内存；`elapsedSeconds` 暂停期间仍计时；无持久化 | Room `active_skill_sessions` 实体 + 跨进程恢复（恢复为 PAUSED）+ 暂停不计时 + completion 幂等（event_id） |
| Skill 契约字段端侧未消费、无白名单分发器 | `ApiClient`/`LocalRepository.parseSkillsArray` 只解析 7 个字段；UI 只有 step-by-step 一种渲染 | 扩展 `SkillDisplay`（action_type/estimated_duration/completion_schema/safety_constraints/revision）；`action_type` 白名单 5 个原生 Compose Renderer；未知类型 fail closed |
| Onboarding 要求用户填内部字段 | `OnboardingScreen` 手填「机构邀请码 / 试点用户 ID / 机构配置令牌」；后端无激活码路由 | 单字段 activation code → `POST /v1/onboarding/verify-code`（复用 `User.external_ref` + `create_access_token`）；七态状态机本地持久化 + 后端资源可推导 |
| CI 深度不足 | backend 无 mypy/PG/coverage/contract drift；actions 用 @v4/@v5 可变 tag；无 contract test | 后端 mypy+PG service container+alembic PG round-trip+coverage+OpenAPI drift；android connected test 矩阵；Android↔Backend contract manifest；security CodeQL/dependency review/pip-audit/osv-scanner/trivy；actions pin 到 commit SHA |

架构模式：沿用现有分层（FastAPI 路由→服务→SQLAlchemy；Android MVVM-ish UI→Repository→Room），不引入新框架。调度继续使用前台服务协程 + WorkManager 上行（02b 已决策）。

### 1.2 边界不变量（本设计必须保持）

1. 被动数据（DerivedFeature）**不做**情绪/危机/自杀推断：不新增 mood 类工具、不恢复 RED 被动升级。
2. raw 传感数据不上云、不落盘（Room v4 已删 sensor_samples，本设计不新增任何 raw 持久化）。
3. mic 默认关、可选；`mic_opt` 缺失不产生 gap。
4. Skill 仅 signed 下发；action_type 白名单外不下发、不执行、fail closed。
5. 审计哈希链 / immutability guard / escalation 生命周期 / SLA 升级（通知≠接管）不变。
6. tenant isolation / RBAC / step-up / consent gate / SQLCipher / Keystore / AES-GCM 不变。
7. GET 只读无副作用；410 语义沿用（有效身份 → 410 Gone，认证链保留）。

## 5. 分项设计（A–I）

### A. sources_present 契约统一设计

**现状核实**：`gap_finder.py:57` 用 `{f.source for f in day_features}` 判断覆盖；`sources_present` 在 models/schemas/profile.ingest_feature 已存在且 Android FeatureExtractor 已产出（FeatureExtractor.kt:96-102），但 gap_finder 完全未消费 → 多窗口同 source 实际覆盖被误判为缺失（defect 1）。

**新算法**（`gap_finder.py`）：

```
def _row_sources(row) -> set[str]:
    if row.sources_present:            # v0.6+：窗口内实际信号源（权威）
        return set(row.sources_present)
    return {row.source}                # legacy fallback：空列表时回退单数 source

present = set().union(*[_row_sources(f) for f in day_features]) if day_features else set()
```

规则：
1. **并集**：当日所有窗口 `sources_present` 的并集为权威覆盖集。
2. **fallback**：某行 `sources_present` 为空/None（旧客户端或历史数据）→ 用该行 `source`。
3. **mic_opt 可选**：不在 `EXPECTED_SOURCES`（仍为 accel/gyro/screen/notification/app_activity 五项），缺失**不**产生 gap；存在则并集自然包含。
4. **health 不强制**：不在 `EXPECTED_SOURCES`，不擅自 mandatory；若未来要强制需产品确认后单独加。
5. **gap_id 幂等**：`no_data` / `source_missing_{source}` / `observation_insufficient` 保持稳定；跨日运行重复产生相同 id 的 gap（runner 侧 `gaps_found` 覆写、Skill 归纳按 content_hash 幂等，无新表）。

**同型问题检查与修复点**：
- `DailyNarrative.gaps`（models.py:264，profile.py:77 恒 `[]`）：当前为「预留」字段；最小改动保持写路径 `[]`，缺口真值由 `SandboxRun.gaps_found` 承担。**修复点**：不改写路径，仅文档标注 gaps 字段为 legacy 预留（B 类）。
- `build_daily_narrative` events（profile.py:73-76）只写 `source/summary`：**修复点**：events 增加 `"sources_present": list(f.sources_present or [])`（事实性覆盖信息，非情绪语义；Android TrendScreen 可展示覆盖，不影响契约）。
- `rebuild_profile` observation_days（profile.py:136）按 `window_start.date()` 去重计数，是「天数」非「source 覆盖」，语义正确不改；可选 P2：traits 增加 `sources_present_union`（供机构工作台观测）。
- `audit_day` summary（audit_day.py:58-63）：**修复点**：增加 `"sources_present": sorted(union)`，供 runner audit metadata 观测；gap_finder 仍自查询 day_features（单一口径），不依赖 audit_summary 传入。
- `tenant_portrait`：只读 observation_stats/active_users，无 singular source 逻辑，无需改。

**测试更新**：test_sandbox_loop 新增：并集抑制误报、空 sources_present fallback、mic_opt 缺失无 gap、health 不强制、legacy 单 source 行为保持。

### B. Android sensing 窗口 ACK 语义重构

**现状核实**：`SensingWindowScheduler.flushWindow`（scheduler 79-111 行）：`flushedWindowStarts.add` 在最前 → `extractFromHub`（快照）→ `mic.snapshotAndClear()`（破坏性）→ `hub.clearAll()`（无条件清空）→ `onWindowReady`（落库+入 outbox）。任一持久化失败时原始缓冲已清空且窗口已标记 flushed → **静默丢失**（defect 6 确认存在）。

**目标时序**：
```
snapshot(非破坏) → extract(纯函数) → transactional persist + outbox →
    persist 成功 → clear consumed(仅本窗口快照项) → SyncWorker.enqueue
persist 失败 → 保留快照/缓冲 → 窗口不进 flushed 集 → bounded retry
```

**具体修改点**：
1. `SensingEventHub.kt`：
   - 新增 `data class HubSnapshot(accel, gyro, screen, notifications, appActivities, micDerived)`。
   - `fun snapshotAll(): HubSnapshot`（各 deque `toList()`，非破坏）。
   - `fun clearConsumed(snapshot: HubSnapshot)`：对每个 modality `buffer.removeAll { it in snapshot.xxx }`。FloatArray 用引用相等（数组不重写 equals），其余 data class 用值相等——正是「只清本窗口已消费项，不清下一窗口新到项」的语义。
   - 保留 `clearAll()` 仅用于 consent revoke / stop（不用于 flush 路径）。
2. `MicDerivedFeatureSource`（MicCollector.kt）：
   - 拆 `snapshot(): List<MicDerivedFeature>` + `clearConsumed(list)`；`snapshotAndClear()` 删除或标记 deprecated（scheduler 不再调用）。
3. `SensingWindowScheduler.kt`：
   - `flushWindow` 返回 `WindowFlushResult { SUCCESS, FAILURE_RETRYABLE }`。
   - `onWindowReady: suspend (List<DerivedFeatureInput>) -> Boolean`（true=持久化成功）。
   - `flushedWindowStarts.add(startMs)` 移到 persist 成功之后；失败时放入 `pendingRetries[startMs]`，`MAX_WINDOW_RETRY=3`，超限丢弃窗口并记录 `consecutivePersistenceFailures`。
   - 成功路径：`hub.clearConsumed(hubSnapshot)` + `mic.clearConsumed(micSnapshot)`。
4. `PassiveSensingService.kt`：
   - `startSensing` 回调改为：`c.repository.saveDerivedFeatures(inputs)` 返回 Boolean → `SyncWorker.enqueue` → true；失败返回 false（不 enqueue）。
   - `stopSensing`：`scheduler?.stop()` + 清空 pendingRetries + `hub.clearAll()`（consent revoke 立即清内存，不补发）。
   - consent revoke 路径（`performPassiveSensingStop`，OtherScreens.kt:273-294）已 `clearAll()`，补充：清 scheduler retry 状态（通过 stopSensing）。
5. `LocalRepository.kt`：
   - `suspend fun saveDerivedFeatures(inputs: List<DerivedFeatureInput>): Boolean`：`db.withTransaction { inputs.forEach { insertFeatureVector; enqueue } }`，异常捕获返回 false；成功才 `preferences.lastSuccessfulCollection = now`。
   - 单条 `saveDerivedFeature` 保留为兼容（委托 batch）。
6. `EchoDatabase.kt`：DAO 增加批量 `insertFeatureVectors(list)`（REPLACE）；withTransaction 内循环亦可，批量方法为性能优化。
7. `AppPreferences.kt`：
   - `lastSuccessfulCollection`（已存在，语义=最近成功采集）
   - `lastPersistenceFailure: Long?`（最近一次窗口持久化失败时间）
   - `consecutivePersistenceFailures: Int`（连续失败计数；成功后清零）
   - 暴露 StateFlow 供 SupportScreen 展示。
8. `OtherScreens.kt` SupportScreen：展示「最近成功采集 / 最近持久化失败 / 连续失败」观测行（不暴露内部 HTTP 码）。

**不写原始数据到磁盘**：Hub 缓冲纯内存；feature_vectors 只存 summary(密文)+vector；无新 raw 落盘路径；Room v4 已删 sensor_samples（不恢复）。

### C. ActiveSkillSession 持久模型设计

**现状核实**：`SkillRunSession`（SkillCardHost.kt:52-112）纯内存；`elapsedSeconds` 在 PAUSED 状态仍继续计时（pause 不记录时间）；process death 后会话丢失；completion 依赖 `SkillCompletionInput.eventId`（每次终端操作新生成，服务端 tenant+event_id 幂等）。

**Room Entity `active_skill_sessions`（Room v5）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| sessionId | String PK | `skse_<uuid>` |
| skillId | String | 后端 Skill.id |
| skillVersion | Int | 快照版本 |
| skillRevision | Int | 快照修订号 |
| actionType | String | 白名单校验（加载时不在白名单 → 丢弃会话） |
| status | String | `running` / `paused` |
| currentStep | Int | 当前步骤 |
| startedAt | Long | 会话创建 epoch ms |
| accumulatedActiveMs | Long | 已完成活动段累计（暂停前） |
| segmentStartedAtMs | Long? | 当前 RUNNING 段开始；paused 时为 null |
| pausedAt | Long? | 最近暂停时间 |
| updatedAt | Long | 最后变更 |

**duration_seconds 语义**：
```
activeDurationMs(now) =
    running: accumulatedActiveMs + (now - segmentStartedAtMs)
    paused : accumulatedActiveMs          # 暂停不计时
completion 上报 duration_seconds = activeDurationMs / 1000
```

**跨 process death 恢复流程**：
1. 进程重建（AppContainer/应用启动或 SkillCardHost LaunchedEffect）→ `repository.loadActiveSession()`。
2. 存在且 status=running → **恢复为 PAUSED**（不自动计时，避免进程死亡期间虚增时长）；UI 展示「上次进行中 · 用时 X 秒 · 继续 / 结束」。
3. 存在且 paused → 原样恢复 paused。
4. 用户「继续」→ resume（segmentStartedAtMs=now）；「结束」→ complete/stop。
5. 会话被 service 主动清理（DSR delete、Skill retired 等）→ 删除行。

**completion 幂等**：终端操作（complete/stop）时生成 event_id → `saveSkillCompletion` 在同一 `withTransaction` 内「删除 active_skill_sessions 行 + 插入 outbox(skill_completion)」→ SyncWorker 上传 `POST /v1/skills/completions`（服务端 tenant+event_id 幂等）。进程死在 enqueue 前 → 会话行仍在 → 恢复流程兜底；死在 enqueue 后 → outbox 重试兜底。

**迁移**：`MIGRATION_4_5`（AppContainer.kt）`CREATE TABLE active_skill_sessions (...)`；`DatabaseMigrationTest` 增 v4→v5 断言。

### D. action_type whitelist dispatcher 设计

**现状核实**：后端白名单 `ACTION_TYPE_WHITELIST=(guided_steps, reflection_prompt, breathing, journaling, checklist)`（schemas.py:186-192）；SkillOut/脱敏已带 action_type/estimated_duration/completion_schema/safety_constraints/revision（sanitizer.py:77-90）；但 Android `parseSkillsArray` 只解析 id/name/version/triggerConditions/guardrails/steps/status（LocalRepository.kt:605-617）→ 契约字段端侧未消费（defect 7）。


各 Renderer 接口与数据：
- `GuidedStepsContent`：现有 step-by-step（下一步/暂停/完成/停止）。
- `BreathingContent`：呼吸引导（圆环动画，按 estimatedDuration 秒或步骤推断节奏）；暂停/继续/完成/停止。

1. `SkillCardHost` 启动前校验 `skill.actionType in whitelist`，否则不渲染「开始」，展示「此能力暂不可用」。
2. `ActionRenderer` else 分支 `BlockedContent`：不调用 `recordSkillCompletion`。
3. `SkillListScreen` 过滤 `actionType` 不在白名单的卡片（与后端 signed+whitelist 下发双保险）。

### E. Onboarding 后端契约设计

**现有路由核查结论**：`POST /v1/tenants`（X-Bootstrap-Key，仅租户创建）不可复用为端侧激活；`POST /v1/users`（admin/professional 创建用户）是机构侧通道；`POST /v1/onboarding/consents`、`POST /v1/onboarding/l0`、`POST /v1/onboarding/emergency-contact`、`GET /v1/onboarding/consents/latest` 均可复用。**无** activation-code 端到端验证路由（缺陷：OnboardingScreen 要求手填「机构邀请码/试点用户 ID/机构配置令牌」内部字段，defect 8）。

**新增薄路由 `POST /v1/onboarding/verify-code`**（复用现有数据模型，无新表；P2 可选加 external_ref 索引）：
```
Request  : { "code": str(8..80) }
Logic    : 跨租户查 User.external_ref == code
           - 0 命中 → 404 "无效激活码"（不泄露租户存在性）
           - 命中且 user.status == "restricted" → 403 "该激活码已受限，请联系机构"
           - 命中且 user.status == "active" → create_access_token(subject=user.id, tenant_id=user.tenant_id, role="user")
Response : {
   "user_id": user.id,
   "access_token": "<opaque JWT>",
   "consent_versions": {"psychological_data": "...", "passive_sensing": "...", "voice_features": "..."},
   "l0_decision": "eligible" | "human_assessment" | "urgent_human" | null,   # 从 OnboardingScreening 最新行推导
   "restricted": false
}
audit    : onboarding.verify（actor=user, object=user_id）
```
**不暴露内部字段**：响应无 tenant_id / role / external_ref / bootstrap 信息；JWT 载荷内部字段对用户透明。

**七态状态机（Android `AppPreferences.onboardingState`，可被后端资源推导）**：
```
not_started → code_verifying → code_verified → consents_submitted → l0_submitted → completed
                                                                       ↘ restricted（L0 excluded / user.status）
                                                                       ↘ withdrawn（DSR revoke_service）
```
- 每态持久化 `onboardingState`；状态推进顺序固定。
- 后端同步：consents 经 `GET /v1/onboarding/consents/latest`；L0 决策由 verify-code 响应携带（服务端 OnboardingScreening 最新行）；restricted 由 `user.status` 决定（verify-code 返回 403 或 restricted=true）；withdrawn 由 DSR revoke_service 状态（Android 端已有 revoke_service 按钮，onboarding 完成后不可逆进入）。
- OnboardingScreen 改动：删除 3 个内部输入框，改单「激活码」字段；verify-code 成功后存储 user_id（加密 access_token），继续走 consents→L0→（可选）紧急联系人→completed。

**测试**：`test_onboarding_verify_code.py`（命中/未命中/restricted/幂等/不泄露内部字段/无 token 401）；`OnboardingGateTest` 更新。

### I. 故障注入矩阵设计

| # | 场景 | 注入点 | 预期行为 | 死信/恢复语义 |
|---|---|---|---|---|
| 1 | offline | SyncWorker 无网络 | 事件留 outbox；`Result.retry()`；SyncState=OFFLINE | 不丢、不 dead-letter |
| 2 | connect/read timeout | ApiClient | 抛异常 → incrementAttempts + RETRY | 超 MAX_ATTEMPTS(10) → DEAD_LETTER |
| 3 | DNS 失败 | ApiClient | 同 timeout（异常 → RETRY） | 同 2 |
| 4 | 401 | POST 上行 | KEEP_PENDING（登录失效） | 永不 dead-letter；UI BLOCKED_BY_AUTH |
| 5 | 403 | POST 上行 | KEEP_PENDING | 同 4 |
| 6 | 410 + deprecated 类型 | checkin/journal/questionnaire/practice | DELETE_AND_MIGRATE（terminal + telemetry） | outbox 删除，不重试 |
| 7 | 410 + 非 deprecated | derived_feature 等 | DEAD_LETTER | outbox 删除 + dead-letter 记录 |
| 8 | 412 consent 撤回 | POST 上行 | KEEP_PENDING → 超限 DEAD_LETTER | UI BLOCKED_BY_CONSENT |
| 9 | 429 Retry-After | POST 上行 | recordRetryAfter + RETRY（WorkManager 指数退避） | 超限 DEAD_LETTER |
| 10 | 500 | POST 上行 | RETRY | 超限 DEAD_LETTER |
| 11 | malformed 响应 | GET skills/narratives/profile | 解析失败 → loadFailed=true → UI 重试（不伪装 no_data） | 无 outbox 影响 |
| 12 | 服务重启 | PassiveSensingService | 窗口对齐恢复；内存缓冲随进程消亡（空）→ 无脏数据/无重复 | flushed 集丢失但缓冲空，安全 |
| 13 | duplicate 事件 | POST ingest/completions | 服务端幂等（tenant+event_id）→ 200 idempotent_replay → DELETE | outbox 删除 |
| 14 | process death | ActiveSkillSession 运行中 | 恢复为 PAUSED，时长不虚增；提示继续/结束 | 会话行保留直至显式终态 |
| 15 | 窗口持久化失败 | saveDerivedFeatures | WindowFlushResult.FAILURE → bounded retry(≤3) → 记录 consecutivePersistenceFailures | 快照未清，无静默丢失；超限丢弃该窗口但可观测 |
| 16 | consent revoke | SupportScreen/权限撤回 | 立即清内存 + 不补发；写 revoke 证据入 outbox | 后续零新特征 |
