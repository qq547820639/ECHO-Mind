## 1. 现状基线：v0.7.0 代码事实（一句话结论）

**感知与画像主链已经完整，且比方案假设的更好；方案要新增的「Presence 层」在代码里为零。** 差距不在底层链路，而在前台体验与状态语义。

## 2. 差距分析（按方案章节，逐条对照代码）

### A. 授权与苏醒（§11、§12、§13）

| 方案要求 | 现状（`ui/OnboardingScreen.kt`，523 行） | 差距与改动点 |
|---|---|---|
| 三步：认识 ECHO → 隐私承诺 → 核心感知授权 | 六步：WELCOME → PORTRAIT_EXPLANATION → CORE_DATA_CONSENT → MINIMUM_SENSING → BASELINE_WARMING_UP → DONE（L507-511） | 合并为三步；删 BASELINE_WARMING_UP 与 DONE |
| 每一次授权立即反馈、以系统真实状态为唯一事实来源 | 已有 `pendingUsageVerify/pendingNotifListenerVerify` + ON_RESUME 回填（L101-123），但 `onAuthorize` 仍先乐观置 `usageAuthorized=true`（L331-335）；SENSOR 行是纯本地置 true（L316），无系统校验 | 删乐观置位；所有行在 ON_RESUME 统一重读 `capabilityState()`；SENSOR 行改为「硬件可用性」而非假授权 |
| 最后一个核心权限成功后：按钮消失 → 图形苏醒 → 「ECHO 已开始了解你」→ 自动进主页，无 DONE | 现在必须点 DONE 页「进入应用」才 `finishOnboarding()` | `finishOnboarding()` 改为自动触发；新增 AWAKENING 过渡态（约 1.5-2.5s 视觉过渡后 `onComplete()`） |
| Core / Enhancement / Sensitive Optional 三级 | 已有「核心 vs optional」两级（SENSOR 核心；USAGE/NOTIFICATION/MIC optional） | 重归类：SENSOR+SCREEN=Core；USAGE/NOTIFICATION=Enhancement（**移出 onboarding**，核心体验后追加提示）；MIC=Sensitive Optional（移出 onboarding，仅支持页单独授权） |
| Step 2 隐私承诺三句话 | PORTRAIT_EXPLANATION 现有文案是链路解释，非三句承诺 | 文案替换（保留「不会因一个行为定义你的心理状态」等契约句） |

注意点：现有 WELCOME 页还有 18 周岁确认与边界确认两个 checkbox（L210-211）——方案 Step 1 未提。建议保留为 Step 1 内的勾选项（法律准入门，不是「手续」），见决策 Q5。

### B. Sensing Runtime State（§14）—— P0 核心

| 方案要求 | 现状 | 差距 |
|---|---|---|
| 六态：NOT_AUTHORIZED / STARTING / ACTIVE / DEGRADED / SYSTEM_PAUSED / USER_PAUSED | `AppPreferences.sensingActive`（布尔，L221-229）+ `CapabilityState`（四态，仅表达单能力）+ onboarding 七态（是激活生命周期，不是运行态） | 无统一运行时状态；需新建纯函数状态机 |
| 「关闭」必须永远表示用户行为 | 三个错位路径：① `sensingActive` 只在服务 start/stop 写——系统杀进程后不清理，僵尸 true；② `capabilityState(..., sensingEnabled=false)` 时**所有**能力返回 DISABLED——「系统已授权 usage 却显示关闭」；③ flag 拉取失败 fail-closed=false → 用户已授权但服务不启动，无解释 | 新建 `resolveSensingRuntimeState()` 以「系统权限真实状态 + 用户开关 + 服务活跃心跳」为输入；flag/网络/同步错误一律映射到 SYSTEM_PAUSED/DEGRADED，绝不映射 USER_PAUSED |
| 各态用户文案 | 只有 SENSING_DISABLED 一条（`PORTRAIT_COPY_SENSING_DISABLED`） | 六态各配文案 + CTA（如 SYSTEM_PAUSED →「ECHO 暂时休息了 · 查看原因」） |

设计要点（已与现状对齐）：
- 输入：`userConsentOn`（DataStore）、`serviceStarted`、`lastCollectionAt` 新鲜度（复用 `lastCollectionTimestamp` + `hasRecentCollection`，但运行时态用更短的过期阈值，如 60 分钟，区别于趋势页的 3 天）、`capabilityState()` 全表、`consecutivePersistenceFailures`。
- 判定顺序：consent 关 → USER_PAUSED；consent 开且服务未运行 → SYSTEM_PAUSED（系统杀/电池策略）；服务运行但采集心跳过期 → SYSTEM_PAUSED（假活检测）；optional 能力 DENIED/UNAVAILABLE → DEGRADED；刚授权尚无窗口 → STARTING；其余 → ACTIVE。
- `sensingActive` 布尔保留为原始输入，不再直接驱动 UI 文案。

### C. 首日画报与成长模型（§15、§16）

| 方案要求 | 现状 | 差距 |
|---|---|---|
| Day0 SEED：标题「初见」，不伪造个性判断 | Day0 = WARMING_UP 文案 + X/7 进度 + coverage 百分比（`TodayScreen.kt` L172-183）；本地引擎会拼当天事实句 | 有「内容」但无「画报」。SEED 是**存在性表达**（初见/已观察 N 分钟/初始生命场），与画像 abstain 契约不冲突——它不是伪造观察，是陪伴状态 |
| Day1-2 DISCOVERING：真实观察，不比 baseline | WARMING_UP 已显示当天事实句（`factsOnly`，L175-181） | 文案微调即可（「ECHO 已经开始看到一些屏幕使用节律」风格） |
| Day3-6 EMERGING：tentative patterns，语言带不确定性 | EARLY_BASELINE（3-6 天）已存在，`PortraitSummaryOnly` | 语义基本对应，仅措辞与视觉结构渐进 |
| Day7 KNOWN：仪式「我开始认识通常的你了。」 | 已有一次性解锁横幅 `PORTRAIT_COPY_BASELINE_UNLOCKED`（「你的基线已经成型…」）+ `consumeBaselineUnlocked()` | 换仪式文案（见决策 Q8），视觉发生一次明显但克制的成长变化（P1 实现） |
| 四阶段映射 | 后端三态 + 客户端无「安装日」锚点 | 新增客户端锚点 `firstAwakenedDate`（苏醒瞬间写入）；maturity = f(今天 - 锚点)。老用户回填：取本地最早 feature window 日期或基线起始日 |

### D. Ambient State 与状态向量（§6、§29）

现状：无。设计要点：
- 新增纯 Kotlin 模块 `presence/`（与 `localportrait/` 同模式：纯逻辑、可 JVM 单测、golden 用例）。
- 输入：当日 aggregate（活跃水平、事件密度、活跃起始/结束分钟）、近期窗口特征、baseline 偏差（z/MAD）、覆盖度、置信度 → 输出 `AmbientState {QUIET, ACTIVE, DENSE, SLOW, LATE, TRANSITION, UNKNOWN}` + 向量 `(activation, regularity, density, deviation, confidence)`。
- 计算位置：**端侧**（本地模式 + 离线都成立，wallpaper 不能依赖网络）；订阅用户可选服务端增强（P4）。
- 更新频率：分钟级（挂到 5 分钟窗口持久化钩子上，或 15 分钟去抖），与渲染 60fps 完全解耦——两个时间尺度，符合 §10。
- 状态之间连续过渡：视觉层做数值插值，AmbientState 只是语义标签，向量才是渲染输入。
- **词表门禁**：QUIET/ACTIVE 等是机器内部态。若任何词要用户可见（如锁屏「今天比较安静」），必须过 Psychology Review——注意「安静/活跃」在 Phase 6.3 是 REWRITE 词（画像文案中已替换为「移动较少/移动较多」），锁屏若重新引入需要产品裁决（决策 Q3）。

### E. EchoPresenceState 与架构分层（§28）

现状：无统一状态对象；Today 读 `PortraitUiState`，Support 读 `sensingActive`+时间戳，各页各算。

设计要点：
- `EchoPresenceState(timestamp, maturity, ambientState, activityLevel, rhythmDelta, coverage, confidence, visualSeed, publicSummary, privateSummary)` 定义为纯数据类。
- `EchoStateStore`：进程内单例 StateFlow（AppContainer 注入）+ 落盘最近一版快照（App 进程死亡后 wallpaper 恢复用）。WallpaperService 与 App 同进程，可直接读 Store；异进程兜底读快照。
- 唯一写入方：`AmbientEngine`（窗口持久化后触发）；Today/Wallpaper/Dream 都是只读消费者。彻底消灭「首页说运行、趋势说关闭、壁纸另一套」。
- `visualSeed`：确定性派生（userId hash + 日期 + maturity；可复用已有 `baseline_snapshot_digest` 作为种子来源之一——端上与后端同算法产出、可复现），Day30/Day100「个人特征」由 seed 演化而来，不需要存储大状态。

### G. 趋势页（§18）

现状：`ui/TrendScreen.kt`（449 行）已是 7/28 天 Portrait Timeline + 七态 + NO_DATA 八原因 + 维度符号矩阵 + 28 日稳定性综述（`portraitStabilitySummary`：最接近/变化较明显）+ 免责文案。

差距（P1 后段或 P4）：
- narrative 优先化：现在矩阵是主体，综述是配角；方案要求「这一周/最近一段时间/我正在发生怎样的变化」叙事优先、图表辅助。
- 「查看依据」：需要每句叙事可点开对应维度 facts（数据链路已具备，是 UI 重组）。
- 「长期」尺度：后端无 >28 天窗口分析，落到 P4（More Intelligence）。工程事实：后端 legacy `narratives.py`/trends 链仅剩 Checkin 兼容且已撤公开（`docs/current/30_Phase9_Legacy_Audit.md` B 类），「长期」叙事不能复用旧链，需要新建 narrative 服务（依据可复用现有 `explain.py` facts 与 z 值）。

### I. 订阅（§20）

现状：单档 `standard`，激活码授予，权益 = 云端同步备份 + 长周期分析 + 专业支持 + 能力练习；本地免费版 = 除上述外全功能。工程钩子：`services/subscription.py` 为单档 + `retention_days` 固定 28 天（无按档位保留期）——多档需要 plan 枚举扩展、retention_days 按档位区分、门禁按档位下沉（现 `require_active_subscription` 只在 skills/escalations 两处）。

与方案的差距：
- 方案免费版新增权益「ECHO Presence / Wallpaper、ECHO Dream、基础能力」——这些能力尚不存在，**先建能力、后放进免费版**，顺序上不冲突。
- 方案订阅分层 More Memory / More Continuity / More Intelligence / More Human Support / More Service —— 现单档；需要产品定义档位矩阵（决策 Q4）。生命周期机制（到期冻结云端能力、本地不受影响）可复用。
- 冲突点：能力练习 402 门禁 vs 「基础行动能力免费」原则，处理顺序见 §4 P0/P1。

### J. Presence 系统（§8、§10、§25、§34、§35）

现状：零。平台约束已核对（minSdk 26 / compile & targetSdk 36）：
- `WallpaperService`：需 `BIND_WALLPAPER` + meta-data `android.service.wallpaper`；`onVisibilityChanged(false)` 必须停渲染；系统区分 Home/Lock 渲染上下文（API 34+ 的 `WallpaperService.Engine` 可感知）。墙纸引擎与 App 同进程，可直接读 `EchoStateStore`。
- `DreamService`：需 `BIND_DREAM_SERVICE` + 用户在系统设置手动选择（`Settings.ACTION_CHANGE_SCREENSAVER_SETTINGS`）；仅充电/底座 + 空闲运行（系统决定，方案 §8.2 描述正确）；部分 OEM 砍掉了屏保入口——产品文案不能承诺全设备可用。
- 低功耗验收（§10/§34）：不可见 0 渲染；可见时帧率上限（如 30fps）+ 只在状态变化时重算参数；充电场景可放宽。**能耗指标进验收清单**（见 §8）。
- 锁屏隐私（§21）：`publicSummary` 白名单词表（图形/时间/非敏感节律语言），`privateSummary` 只在应用内可见；默认「仅视觉」档。注意与 Phase 6.3 REWRITE 词表的交叉（决策 Q3）。
- 状态低频更新：`AmbientEngine` 5-15 分钟重算一次，视觉参数插值过渡——架构上直接满足 §10。

### K. 通知策略与信任中心（§24）

现状：常驻通知 `buildNotification()`：title「ECHO Mind」/ text「被动采集中（端侧处理）」/ channel「被动采集」IMPORTANCE_LOW（`PassiveSensingService.kt` L214-228）。支持页已有「数据与感知」区块（采集/同步时间戳、连续失败计数、开关）。

差距（P0）：
- 文案改为「ECHO · 正在了解今天」（禁止「后台服务正在运行」类）。
- 通知点击 → 直达应用内「数据与感知」信任控制中心（PendingIntent + extra 定位）。

## 3. 关键架构决策（建议在开工前评审）

- **D1 计算位置**：Ambient State 与 EchoPresenceState **完全端侧计算**（local-first 架构 + wallpaper 离线可用 + 无上云隐私审计负担）；backend 只在 P4「长期个性化/More Intelligence」时介入。分钟级状态向量**不上云**（避免与数据最小化契约冲突，见后端审计结论③）。
- **D2 成熟度映射**：SEED=安装/苏醒当天，DISCOVERING=1-2 天，EMERGING=3-6 天，KNOWN=≥7 天；由客户端 `firstAwakenedDate` 锚点推导，后端基线算法不动。老用户回填取本地最早特征窗口日期。
- **D3 视觉引擎分层**：`presence/` 纯 Kotlin 参数计算（可单测）→ 三种渲染器：Compose Canvas（应用内，P1）、`WallpaperService` Engine 的 SurfaceHolder Canvas（P2）、`DreamService` 同渲染器（P3）。风格资产（粒子/流体/柔性几何）待品牌定稿（决策 Q7），但引擎接口与状态解耦先行。
- **D4 状态机关系**：`SensingRuntimeState`（感知健康，六态）与 `PortraitStatus`（画像内容，九态）**正交**。Today 用两者联合渲染：感知态决定头部生命区与通知，画像态决定文字内容。不合并成一个枚举。
- **D5 Day0 SEED 的契约定位**：SEED 是「存在与陪伴」的表达（初见/已观察时长/初始生命场），不是画像输出——因此不违反「数据不足 abstain」。SEED 展示的事实必须全部可追溯（观察时长、覆盖度），绝无「个性判断」。
- **D6 词表扩展**：新增 PRESENCE 词表（监测/检测等禁令 + publicSummary 白名单），并入现有 Psychology Review 门禁与 CI。
- **D7 苏醒瞬间的迁移语义**：v0.7 老用户已完成 onboarding，永远不会看到新苏醒瞬间——需要「回归用户」处理：首次进入 Today 时若 maturity 可回推，展示一次克制的 SEED/成长回顾（可选），不强行重放授权。

## 13. 交付顺序与依赖总览

```text
P0（信任修复）─────────────────────────────► 可独立发布
   │  firstAwakenedDate / RuntimeState / watchdog
   ▼
P1（应用内 Portrait）◄── 依赖 P0 的苏醒锚点与状态引擎
   │  EchoPresenceState / EchoStateStore / AmbientEngine
   ▼
P2（Wallpaper + Presence 设置）◄── 依赖 P1 的 Store 与视觉引擎
   ▼
P3（Dream）◄── 复用 P2 渲染抽象
   ▼
P4（Personal State Intelligence）◄── 依赖基线稳定 + 反馈数据积累（≈Day7 后）
   ▼
P5（Affective，契约先行）◄── 七项前置全部完成，独立评审，随时可被否决
```

相对工作量：P0 = M（改流程 + 状态机 + 测试），P1 = L（新引擎 + 视觉 + 布局），P2 = M-L（服务 + 设置 + 能耗验收），P3 = S-M（复用 P2 抽象），P4 = L（长期分析 + 个性化），P5 = XL 且主要成本在非工程（契约/验证/合规）。

> 一句话原则（写入后续所有 PRD）：**用户购买的是体验，不是系统内部 plumbing；ECHO 可以不知道，但不能装懂，更不能把系统故障说成用户关闭。**
